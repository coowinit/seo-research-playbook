# Google Search Console 网站级数据分析

Google Search Console 不只是用来查看“某个关键词排第几”。当网站已经拥有一定数量的产品页、内容页、技术资料和案例后，更重要的任务是把搜索表现拆成可解释的结构，并判断问题到底发生在网站级、目录级、页面级还是查询词级。

本模块重点解决：**查询词 × 页面 × 国家 × 设备 × 时间** 的组合分析，并把数据重新连接到关键词研究、网站架构、页面 SEO、技术 SEO 和内容维护。

---

## 1. 本模块回答什么问题

网站级 Search Console 分析主要回答：

- 整个网站的自然搜索表现是在增长、持平还是下降？
- 增长 / 下降主要来自哪些页面类型、产品目录或内容目录？
- 品牌搜索和非品牌搜索分别发生了什么？
- 哪些页面获得了新的搜索需求？
- 哪些页面出现搜索意图偏移？
- 哪些查询由多个页面同时承接，是否真的存在页面职责冲突？
- 哪些国家 / 地区正在增长或偏离目标市场？
- 手机与电脑的表现差异是否值得进一步检查？
- 新内容是否产生了增量，而不是简单替代旧页面？
- 网站改版、迁移或重大内容更新前后发生了什么？
- 搜索流量变化是否最终转化为产品查看、资料下载、样品申请或询盘？

## 2. Search Console 在整套流程中的位置

```text
业务目标
↓
关键词与页面映射
↓
网站架构
↓
内容与页面 SEO
↓
技术 SEO
↓
发布
↓
Google Search Console
↓
网站级 / 目录级 / 页面级 / 查询词级诊断
↓
保持 / 微调 / 更新 / 扩展 / 合并 / 重构 / 技术修复
↓

```

Search Console 是**验证层**，不是独立于前面工作的另一套 SEO 方法。

## 3. 先确认分析对象和时间范围

开始分析前先记录：

| 项目 | 内容 |
|---|---|
| Search Console 资源 | Domain / URL-prefix |
| 主要市场 |  |
| 主要语言 |  |
| 搜索类型 | Web / Image / Video / News |
| 当前周期 |  |
| 对比周期 |  |
| 是否有网站重大变更 |  |
| 是否存在季节性 |  |
| 是否有已知数据异常 |  |

### 3.1 默认时间比较

常用方式：

- 最近 28 天 vs 前 28 天：观察近期变化。
- 最近 3 个月 vs 前 3 个月：减少短期波动。
- 同比：适合季节性较强的网站。
- 改版前后：适合迁移、结构调整、大规模内容更新。

不要把一种时间窗口固定成所有项目的标准。

### 3.2 长期趋势优先使用周 / 月粒度

日数据适合排查异常和重大事件；周或月数据更适合观察长期趋势，减少周末、节假日和单日波动造成的误判。

## 4. 分析前先理解数据边界

Search Console 不是完整的逐次搜索日志。

### 4.1 匿名查询

部分查询会因为隐私原因不显示在查询表中，但仍可能被计入总点击和总展示。

因此：

> 查询词表格相加的结果不一定等于图表总数。

### 4.2 表格和导出行数有限

Search Console 界面只适合常规分析。大型网站或大量查询需要使用 Search Console API 或批量数据导出。

### 4.3 Canonical 聚合

多数页面表现会归到 Google 认定的规范网址，而不是每一个重复网址。

所以分析某个 URL 之前，应先确认：

- 当前页面 Canonical 是否符合预期；
- Google 选择的规范网址是否一致；
- 网站改版后是否发生规范网址变化。

### 4.4 资源级和页面级聚合不同

图表总数与按页面分组后的表格数字可能因为聚合方式不同而存在差异，不要机械要求两者逐行相加完全一致。

### 4.5 最新数据可能仍是初步数据

最新时间段的数据可能继续变化。重大决策尽量使用已经完整的数据周期，而不是根据当天或昨天的数据立即修改网站。

### 4.6 时区

除 24 小时视图外，Search Console 常规日期数据按太平洋时间统计。与 Google Analytics、CRM、服务器日志或业务订单比较时，应注意时区差异。

### 4.7 官方数据异常

如果全站突然出现无法解释的断崖式变化，先检查 Google Search Console 官方数据异常记录，再判断是否真的属于网站 SEO 问题。

## 5. 网站级分析的标准顺序

建议始终从大到小：

```text
全站趋势
↓
品牌 / 非品牌
↓
页面组 / 目录
↓
国家
↓
设备
↓
具体页面
↓
具体查询词
↓
查询词 × 页面
↓
业务转化
```

不要从一个下降关键词直接推导整个网站的问题。

---

## 6. 第一层：全站趋势

首先只观察：

- 点击
- 展示
- 点击率
- 平均排名

并比较当前周期与对比周期。

| 指标 | 当前周期 | 对比周期 | 变化 | 初步判断 |
|---|---:|---:|---:|---|
| 点击 |  |  |  |  |
| 展示 |  |  |  |  |
| 点击率 |  |  |  |  |
| 平均排名 |  |  |  |  |

### 6.1 常见组合

#### 展示下降 + 点击下降

优先检查：

- 搜索需求是否下降；
- 重要目录是否整体掉量；
- 排名是否下降；
- 是否发生索引 / 技术问题；
- 是否发生网站迁移或 URL 变化；
- 是否存在官方数据异常。

#### 展示增长 + 点击基本不变

可能是：

- 页面开始覆盖更多长尾查询；
- 新增展示主要处于较低排名；
- 新增查询点击倾向较低；
- 搜索结果形态发生变化。

不能自动得出“点击率变差，所以标题失败”。

#### 展示稳定 + 点击下降

继续拆：

- 平均排名是否变化；
- 查询词结构是否变化；
- 点击率是否只在某些页面 / 设备 / 国家下降；
- 搜索结果是否出现新的模块或竞争结果。

---

## 7. 第二层：品牌词与非品牌词

品牌词通常代表已经知道企业或产品品牌的用户；非品牌词更能反映新增搜索需求和 SEO 获客能力。

当 Search Console 提供品牌 / 非品牌筛选时可以直接使用；如果当前资源没有该功能，也可以使用查询筛选或导出数据自行分类。

### 7.1 建议分别回答

**品牌词：**

- 品牌搜索需求是否增长？
- 品牌产品词是否增长？
- 是否出现品牌 + 问题 / 评价 / 安装类搜索？

**非品牌词：**

- 哪些产品主题正在增长？
- 哪些信息型查询带来新增曝光？
- 哪些商业比较查询开始进入更高排名？
- 哪些非品牌流量最终进入产品页或询盘？

### 7.2 不要混合解释

例如全站点击增长 20%，如果主要来自品牌词增长，并不能直接说明非品牌 SEO 内容策略同样增长了 20%。

---

## 8. 第三层：页面组与目录级分析

网站级判断不能只看 Top Pages。

应该根据网站架构建立页面组，例如：

```text
/products/composite-decking/
/products/wall-cladding/
/resources/comparisons/
/resources/installation/
/resources/technical/
/projects/
```

或按页面职责分组：

- 产品大类页
- 产品系列页
- 单产品页
- 比较内容
- 安装指南
- 技术资料
- 项目案例
- FAQ
- 工具

### 8.1 页面组需要回答

| 页面组 | 点击变化 | 展示变化 | 主要问题 | 下一步 |
|---|---:|---:|---|---|
| 产品分类 |  |  |  |  |
| 产品页 |  |  |  |  |
| 比较内容 |  |  |  |  |
| 安装内容 |  |  |  |  |
| 技术资料 |  |  |  |  |
| 项目案例 |  |  |  |  |

### 8.2 为什么目录级很重要

如果全站下降 12%，但：

```text
产品页 +8%
比较内容 +15%
技术资料 +5%
旧博客 -55%
```

真正的问题显然不是“全站 SEO 都在下降”。

---

## 9. 第四层：页面级机会与风险

页面级分析建议至少分成四组：

### A. 高价值增长页

表现增长且与业务高度相关。

动作：

- 保持稳定；
- 加强相关内部链接；
- 补充真实案例和证据；
- 检查能否更自然地连接产品和转化。

### B. 高展示低点击页

不要直接修改标题。

先判断：

```text
查询是否正确
↓
排名区间
↓
品牌 / 非品牌
↓
设备和国家
↓
搜索结果结构
↓
再判断标题 / 摘要
```

### C. 有点击但业务价值低

可能是：

- 查询意图偏移；
- 页面吸引了错误用户；
- 信息内容和产品没有连接；
- 页面应该承担教育而不是直接询盘。

### D. 重要页面持续下降

继续进入：

- 查询词变化；
- 竞争结果变化；
- 页面准确性；
- 内部链接；
- 技术状态；
- 搜索需求变化。

---

## 10. 第五层：查询词分析

查询词不要只按照点击排序。

建议建立以下分类：

| 查询类型 | 含义 |
|---|---|
| 核心查询 | 页面原本计划承接的主要需求 |
| 长尾查询 | 与主题一致但更具体 |
| 新增长查询 | 当前周期明显增长 |
| 新出现查询 | 以前没有明显展示 |
| 下降查询 | 原本有价值但持续下降 |
| 商业机会查询 | 与产品、供应、价格、规格、采购相关 |
| 意图偏移查询 | 开始偏离页面原职责 |
| 无关查询 | 与业务 / 页面职责明显不一致 |

### 10.1 高展示低点击查询

重点判断：

- 当前页面是不是正确承接页；
- 排名是否已经具备优化点击率的意义；
- 标题与查询是否一致；
- 是否需要更明确的答案；
- 是否需要新的独立页面。

### 10.2 排名 8—20 附近的查询

可以作为机会池，但不能机械理解成“全部加内容”。

先检查：

- 用户意图；
- 当前页面是否真正适合；
- 搜索结果主要页面类型；
- 是否有能力增加更好的证据和用户价值。

---

## 11. 第六层：查询词 × 页面

这是判断页面职责和关键词内耗的重要分析。

操作逻辑：

```text
选择一个重要查询
↓
查看 Pages
↓
有哪些 URL 获得展示？
↓
页面职责是否相同？
```

### 11.1 不等于关键词内耗的情况

例如一个查询同时出现：

- 产品分类页；
- 技术指南；
- 项目案例。

如果它们解决的是不同用户任务，不必因为“同词多页面”强行合并。

### 11.2 真正值得处理的冲突

例如两篇文章：

```text
/composite-decking-vs-wood/
/wood-vs-composite-decking/
```

长期承接相同查询、相同意图和相同内容职责，此时才需要认真考虑：

- 合并；
- 重构；
- 内部链接重新分工；
- 规范网址 / 重定向等技术处理。

---

## 12. 第七层：国家 / 地区分析

对外贸企业网站尤其重要。

建议判断：

- 目标国家展示是否增长；
- 非目标市场是否大量增长；
- 同一英语内容在不同国家表现是否不同；
- 是否存在独立国家页面需求；
- 搜索词、产品规格、法规和转化需求是否存在市场差异。

不要因为某个国家曝光增长，就自动建立一个国家子站。

先验证：

```text
持续搜索需求
+
真实业务能力
+
独立内容 / 产品差异
+
长期维护能力
```

---

## 13. 第八层：设备分析

设备差异可以提示问题，但不能单独证明技术错误。

例如手机点击率明显低于电脑，需要继续判断：

- 查询结构是否相同；
- 移动端排名是否相同；
- 搜索结果模块是否不同；
- 页面首屏、导航和转化是否适合手机；
- Core Web Vitals 是否存在移动端问题。

---

## 13.1 补充维度：搜索结果呈现形式

当网站存在视频、商品、富媒体结果或其他特殊搜索呈现时，可以使用 Search Console 的 Search appearance / 搜索结果呈现相关维度进一步拆分。

用途包括：

- 某种结构化数据结果是否带来额外展示；
- 视频类页面与普通网页表现是否不同；
- 某次搜索呈现变化是否造成点击率变化。

这仍然属于辅助诊断，不应该把获得某种搜索呈现形式本身当作稳定排名保证。

## 14. 第九层：时间比较与事件标记

任何重大分析都应该记录同期发生的事件：

| 日期 | 事件 | 影响范围 |
|---|---|---|
|  | 新页面发布 |  |
|  | 标题大改 |  |
|  | URL 迁移 |  |
|  | 内部链接调整 |  |
|  | 产品下架 |  |
|  | 技术故障 |  |
|  | 网站改版 |  |
|  | 市场活动 |  |

否则很容易出现：

> 流量增长了，但不知道是哪次修改产生的。

## 15. 新内容是否产生真正增量

不能只看“新页面有没有流量”。

更合理的判断是：

```text
新页面上线
↓
新页面是否获得目标查询？
↓
原有页面是否明显失去相同查询？
↓
整个主题组总展示 / 点击是否增长？
↓
是否新增商业查询或转化？
```

如果：

```text
新页 +100 点击
旧页 -95 点击
```

则网站整体增量可能非常有限。

所以新内容评估最好同时观察：

- 新页面；
- 原承接页面；
- 整个主题组 / 页面组。

---

## 16. 网站改版前后怎样比较

改版分析至少建立三个层级：

### 16.1 全站

- 点击
- 展示
- 非品牌表现
- 主要国家

### 16.2 页面组

- 产品目录
- 内容目录
- 技术资料
- 项目案例

### 16.3 重点 URL

- 高流量旧页面
- 高转化产品页
- 发生 URL 迁移的页面
- 重要新页面

同时检查：

- 301 是否正确；
- Canonical 是否一致；
- Sitemap 是否更新；
- 页面是否仍被索引；
- 内部链接是否指向新 URL。

不要仅根据改版后 7 天的数据判断成功或失败。

## 17. Search Console 与网站分析 / CRM 的边界

Search Console 主要回答：

> 用户如何在 Google Search 中发现网站？

网站分析工具回答：

> 用户进入网站以后做了什么？

CRM / 业务记录回答：

> 哪些访问最终产生了真实销售机会？

推荐组合：

```text
Search Console
搜索查询 / 页面 / 市场
↓
网站分析
访问 / 页面路径 / 事件
↓
CRM / 表单
询盘 / 样品 / 商机质量
```

不要要求 Search Console 和 Google Analytics 的点击 / 会话数字完全一致，两套系统的统计口径不同。

---

## 18. 大型网站的数据导出策略

### 18.1 小型 / 中型网站

优先使用：

- Search Console 界面；
- CSV / Google Sheets 导出。

已经足够完成多数诊断。

### 18.2 需要自动分析时

可以使用 Search Console API：

- 自定义查询；
- 按 query / page / country / device / date 等维度获取数据；
- 定期保存历史数据；
- 和内部页面分类、CRM 等数据关联。

API 本身仍存在查询和行数限制，不应理解成无限完整日志。

### 18.3 大型网站

如果网站有数万页面或海量查询，可以考虑 Search Console 批量数据导出到 BigQuery。

适合：

- 长期历史保存；
- 页面组 / 目录级自动报表；
- 查询主题聚类；
- 与其他数据源联合分析。

但小型企业站没有必要仅为了“专业”而增加 BigQuery 维护复杂度。

---

## 19. 生成式 AI 搜索表现

当 Search Console 当前资源已经出现相应报告时，可以把 AI Overviews / AI Mode 的曝光作为新增观察层。

建议观察：

- 哪些页面获得生成式 AI 曝光；
- 哪些国家 / 设备较明显；
- 是否以技术资料、原创研究、比较内容或产品页为主；
- 哪些页面值得增加第一手证据。

但不要因为出现 AI 报告，就重新建立一套和传统 SEO 冲突的优化方法。

当前报告可用性和字段可能继续变化，应以 Search Console 实际界面和 Google 最新官方说明为准。

## 20. 常见问题诊断矩阵

| 现象 | 先拆什么 | 可能原因 | 优先动作 |
|---|---|---|---|
| 全站点击下降 | 页面组 / 品牌 / 国家 | 需求、排名、技术、数据异常 | 先定位下降来源 |
| 展示下降但排名相近 | 查询 / 页面组 | 搜索需求下降、查询结构变化 | 看同比和主题趋势 |
| 展示增长点击不增 | 查询 / 排名 / CTR | 长尾扩展、低排名曝光 | 不急于改标题 |
| 展示稳定点击下降 | CTR / 排名 / SERP | 摘要、竞争结果、查询结构 | 按查询验证 |
| 非品牌流量下降 | 产品 / 内容目录 | 获客能力下降 | 拆主题与页面组 |
| 品牌增长非品牌不变 | 品牌 / 非品牌 | 品牌需求增长 | 不夸大 SEO 增长 |
| 一个目录整体下降 | 目录内页面 | 架构、模板、内容、技术 | 目录级排查 |
| 单页大量新查询 | 查询意图 | Google 发现新需求 | 判断扩展或新页 |
| 多页面同查询 | 查询 × 页面 | 正常多意图或职责冲突 | 先判断页面角色 |
| 流量增长询盘不增 | 页面 / 用户阶段 | 流量质量或转化路径 | 结合分析与 CRM |

---

## 21. 网站级诊断输出

一次完整分析最终不应该只输出“流量涨了 / 跌了”。

建议最终形成：

### 事实

- 哪些数据发生变化；
- 变化发生在哪个目录 / 页面 / 查询 / 市场；
- 使用了什么时间周期。

### 判断

- 最可能的问题层级；
- 是否存在其他解释；
- 当前证据可信程度。

### 动作

- 保持；
- 技术修复；
- 页面 SEO 微调；
- 内容更新；
- 新页面；
- 合并 / 重构；
- 内部链接调整；
- 继续观察。

### 明确不做

例如：

- 不因为一周波动大改 URL；
- 不因为平均排名下降 1 位就重写页面；
- 不因为两个页面出现相同查询就立即合并；
- 不因为点击率下降就机械修改所有标题。

---

## 22. 推荐分析频率

### 每周

只做轻量监控：

- 异常跌幅；
- 新索引 / 技术问题；
- 重要页面异常；
- 重大市场变化。

### 每月

进行完整网站级分析：

- 全站趋势；
- 品牌 / 非品牌；
- 页面组；
- 查询机会；
- 国家 / 设备；
- 业务转化。

### 每季度

回到战略层：

- 产品主题增长 / 衰退；
- 网站架构是否合理；
- 内容体系缺口；
- 旧内容治理；
- 新市场和新产品机会。

频率应根据网站规模和业务变化调整。

## 23. 与单页复盘的关系

本模块负责：

> **网站级发现问题。**

当发现某个具体页面需要深入处理时，再使用：

- [单页发布后表现与维护](page-performance-and-maintenance.md)
- [SEO 页面发布后数据与维护模板](../../templates/06-measurement/content-performance.md)

因此：

```text
网站级 Search Console 分析
↓
发现异常 / 机会
↓
锁定页面
↓
单页复盘
↓
具体修改
```

不要把网站级分析和单页维护合并成一张无限扩张的表格。
