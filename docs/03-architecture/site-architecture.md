# 网站架构与内容体系设计

本文件用于把关键词页面映射、竞争网站研究、页面 SEO 和技术 SEO 组合成完整的网站级结构。

它解决的不是“菜单应该放几项”，而是：**一个企业网站应该建立哪些页面、这些页面分别承担什么职责、彼此怎样连接，以及用户和搜索引擎怎样从网站入口发现重要产品、内容和资料。**

---

## 1. 网站架构设计的目标

一个可长期维护的网站架构至少需要同时服务四个目标：

1. **业务清晰**：产品、解决方案、资料和转化入口符合真实业务结构。
2. **用户容易理解**：用户能够快速找到产品、比较信息、技术资料和下一步动作。
3. **搜索需求有明确承接页面**：重要关键词主题有唯一的主要页面职责。
4. **搜索引擎能够发现页面关系**：重要页面通过正常 HTML 链接进入网站导航与内部链接体系。

因此网站架构不是单纯的视觉导航，也不是单纯的 URL 目录设计。

---

## 2. 进入本阶段前需要什么

建议至少准备：

- 市场、语言、客户类型和业务目标。
- 产品大类、系列、型号和真实产品关系。
- 已完成的关键词主题组与页面映射。
- 3—6 个代表性竞争网站的结构观察。
- 现有网站页面清单；新站可用规划清单代替。
- 技术资料、下载文件、案例、安装资料和认证等内容资产清单。
- 主要转化动作，例如询价、申请样品、下载资料、联系销售或查找经销商。

推荐先阅读：

- [关键词研究与页面映射](../02-research/keyword-research.md)
- [竞争网站研究](../02-research/competitor-site-research.md)
- [页面 SEO](../05-optimization/on-page-seo.md)

## 3. 先确定“页面职责”，再设计目录

网站架构设计的基础单位不是菜单名称，而是页面职责。

常见企业网站页面类型包括：

| 页面类型 | 主要职责 | 常见搜索需求 | 常见下一步 |
|---|---|---|---|
| 首页 | 品牌与核心业务总览 | 品牌、公司 | 产品 / 联系 |
| 产品大类页 | 承接核心产品类别 | 核心产品词 | 产品系列 / 样品 |
| 产品系列页 | 细分产品和选择 | 细分产品词 | 单品 / 规格 |
| 单产品页 | 规格、特点与转化 | 型号 / 具体产品 | 询价 / 下载 |
| 应用 / 解决方案页 | 按应用场景组织产品 | 场景需求 | 产品 / 案例 |
| 比较页 | 帮助用户选材 | A vs B | 产品 / 资料 |
| 指南页 | 解释问题和方法 | 信息型查询 | 相关指南 / 产品 |
| 安装页 | 施工和使用 | 安装查询 | 安装文件 / 技术支持 |
| 技术资料页 | 专业决策支持 | 规格 / 标准 / 测试 | PDF / 联系技术 |
| 下载中心 | 集中提供文件 | brochure / datasheet | 文件 / 产品 |
| 项目案例 | 提供真实项目证据 | 项目 / 应用 | 产品 / 询价 |
| FAQ / 支持 | 售前售后问题 | 问题型查询 | 指南 / 联系支持 |
| 工具页 | 辅助选择和计算 | 计算 / 选型 | 产品 / 询价 |
| 关于 / 能力页 | 企业可信度 | manufacturer / company | 联系 / 产品 |

一个页面可以承担多个辅助任务，但应该有一个明确的**主要职责**。

## 4. 产品体系如何进入网站架构

产品结构应优先根据真实业务和用户选择方式设计，而不是根据关键词数量强行制造层级。

典型结构：

```text
Products
├── Composite Decking
│   ├── Series A
│   ├── Series B
│   └── Series C
├── WPC Wall Cladding
│   ├── Series A
│   └── Series B
├── Composite Fencing
└── Railing
```

### 产品层级判断问题

建立一层新页面前，先问：

1. 用户是否真的需要在这一层做选择？
2. 这一层是否有独立的产品范围和介绍价值？
3. 是否有独立的搜索需求？
4. 是否能够提供足够独特的内容？
5. 是否会与上一层或下一层页面职责重复？

如果只是为了多放关键词而建立大量薄弱分类页，应优先合并。

---

## 5. 内容中心不等于“博客”

产品型企业网站的内容资产通常远远超过博客。

推荐按用户任务理解内容体系：

```text
Resources / 资源中心
├── Buying Guides / 选购指南
├── Comparisons / 产品比较
├── Installation / 安装施工
├── Maintenance / 清洁维护
├── Technical Resources / 技术资料
├── Downloads / 下载
├── FAQ / 常见问题
└── Tools / 工具
```

内容中心的目标不是增加文章数量，而是让用户能够沿着真实决策过程继续前进。

例如：

```text
Composite Decking vs Wood
↓
Composite Decking 产品大类
↓
颜色 / 系列 / 技术规格
↓
安装指南
↓
申请样品 / 询价
```

---

## 6. 主题中心与网站枢纽页

当一个主题已经拥有多种内容时，可以使用网站枢纽页连接它们。

例如：

```text
Composite Decking
├── 产品系列
├── Composite vs Wood
├── Cost Guide
├── Installation Guide
├── Cleaning Guide
├── Technical Data
├── Projects
└── FAQ
```

枢纽页的价值是：

- 给用户一个完整入口。
- 让重要页面之间形成稳定连接。
- 减少内容成为孤立页面。
- 明确产品页、指南和资料之间的关系。

不要为了“SEO 架构”强制每个主题都建立一个额外枢纽页。只有当内容规模和用户任务真正需要时再建立。

---

## 7. 主导航怎样设计

主导航应该优先表达网站最重要的业务入口，而不是塞满全部关键词。

一个产品型 B2B 网站可以考虑：

```text
Products
Solutions
Resources
Projects
About
Contact
```

具体是否需要 `Solutions`、`Projects` 或 `Resources`，取决于真实业务。

### 主导航检查原则

- 重要产品大类应能够从稳定导航路径到达。
- 不依赖站内搜索框才能找到重要产品。
- 不把全部文章塞进主导航。
- 不因为菜单空间有限就把核心页面变成孤立页面。
- 链接应使用正常的 `<a href>`，不要只依赖点击 JavaScript 事件。

Google 公开指南明确指出，页面间的链接关系和导航结构会帮助搜索引擎理解网站结构；对于商品类网站，应确保重要商品能够通过类别和子类别链接被发现。

---

## 8. 二级导航与页内导航

主导航解决“进入哪个区域”，二级导航解决“区域内怎样继续浏览”。

例如产品大类页可以提供：

```text
Composite Decking
├── Collections
├── Colors
├── Specifications
├── Installation
├── Comparisons
└── Samples
```

长篇技术页则可以使用页内目录：

```text
Overview
Performance
Dimensions
Installation
Downloads
FAQ
```

页内锚点用于帮助用户浏览同一页面，不应被误用成大量虚拟 URL 页面。

## 9. URL 结构

URL 的核心目标是：**稳定、清晰、一致。**

例如：

```text
/products/composite-decking/
/products/wpc-wall-cladding/
/guides/composite-decking-vs-wood/
/installation/composite-decking-installation/
/projects/residential-deck-project-a/
```

### 不需要机械追求目录层级完全一致

下面两种结构都可能成立：

```text
/products/composite-decking/series-a/
```

或者：

```text
/products/series-a/
```

选择时重点考虑：

- URL 是否长期稳定。
- 页面名称是否可理解。
- 迁移成本是否可控。
- 内部链接、Canonical 和 Sitemap 是否统一使用同一规范网址。

Google 并不单纯根据 URL 路径推断完整网站层级，页面之间真实的链接关系更重要。

---

## 10. 面包屑

面包屑帮助用户理解当前位置，并向上返回网站层级。

例如：

```text
Home
> Products
> Composite Decking
> Series A
```

或：

```text
Home
> Resources
> Decking Guides
> Composite Decking vs Wood
```

原则：

- 表达用户能够理解的典型页面关系。
- 不需要机械复制完整 URL 路径。
- 页面层级调整时同步更新。
- 结构化数据实现参见技术 SEO。

Google 目前在桌面搜索结果中仍支持面包屑展示；移动搜索结果已简化为域名显示，因此不要把面包屑仅理解为搜索结果装饰，它首先是网站导航和层级表达工具。

---

## 11. 内部链接是架构的一部分

网站架构不能只存在于导航菜单里。

推荐至少设计四类内部链接：

### 11.1 层级链接

```text
产品大类
→ 产品系列
→ 单产品
```

### 11.2 主题链接

```text
Composite Decking Guide
↔ Composite Decking vs Wood
↔ Installation Guide
↔ Maintenance Guide
```

### 11.3 内容到商业页面

```text
比较文章
→ 产品大类
→ 样品
→ 询价
```

### 11.4 商业页面到辅助内容

```text
产品页
→ 安装指南
→ 技术资料
→ Warranty
→ FAQ
```

重要页面不应只依赖 Sitemap 被发现。

---

## 12. 点击深度与重要页面

不需要规定“任何页面必须三次点击以内”这样的固定公式。

真正应该关注：

- 核心产品是否有稳定、较短的导航路径。
- 重要页面是否获得足够内部链接。
- 新内容是否容易从现有页面被发现。
- 重要页面是否只能从站内搜索框找到。
- 是否存在没有任何内部链接的孤立页面。

Google 会参考页面需要经过多少链接才能到达、以及获得多少站内链接等关系来理解网站内部的重要性。

---

## 13. 分类、筛选与站内搜索

产品网站常见：

```text
Color
Size
Surface
Application
Material
Collection
```

筛选对用户有价值，但如果每个筛选组合都生成可抓取 URL，可能产生大量低价值或重复网址。

因此架构阶段必须先区分：

### 真正需要搜索落地的分类

例如：

```text
/products/composite-decking/
```

它有独立产品范围、搜索需求和页面价值。

### 仅用于用户筛选的组合

例如：

```text
?color=grey&length=2.9m&surface=woodgrain
```

通常不应该因为存在参数就自动建立独立 SEO 页面。

筛选 URL 的抓取与索引控制属于技术 SEO，架构阶段先确定：**哪些组合值得成为正式页面，哪些只是界面状态。**

---

## 14. 分页、加载更多与无限滚动

类别页、资源中心和案例列表可能需要分页。

架构原则：

- 搜索引擎应能通过可抓取链接发现后续内容。
- 不要假设爬虫会主动点击“加载更多”。
- 如果使用无限滚动，底层仍应有稳定、可访问的分页 URL 或其他可发现机制。
- 分页和筛选不要无控制地产生大量重复 URL。

具体实现归入技术 SEO。

---

## 15. 技术资料与 PDF 怎样进入架构

B2B 网站常见：

```text
Brochure
Technical Data Sheet
Installation Guide
Certification
Warranty
CAD / BIM
Test Report
```

不要简单把所有 PDF 丢进一个下载目录然后结束。

推荐考虑：

```text
技术资料说明页
↓
对应产品
↓
文件说明、适用范围、版本和日期
↓
PDF 下载
```

优点：

- 用户知道文件属于什么产品。
- 可以解释版本和适用条件。
- 产品页面可以稳定链接到资料。
- 文件更新时有清晰的管理入口。

是否允许 PDF 本身索引，根据文件价值和维护方式决定。

## 16. 案例怎样进入架构

案例不只是“新闻”。

可以同时建立关系：

```text
Project
├── Product
├── Application
├── Region
├── Challenge
└── Result
```

案例页应自然链接：

```text
项目
→ 使用产品
→ 对应解决方案
→ 相关技术资料
→ 询盘
```

产品页也可以反向展示真实案例。

这样案例既服务可信度，也服务产品理解和转化。

## 17. 转化路径设计

SEO 架构不能只考虑“用户怎样进入”，还要考虑“进入以后去哪里”。

### 信息型用户

```text
Google
↓
指南
↓
比较 / 技术资料
↓
产品
↓
样品 / 询价
```

### 产品型用户

```text
Google
↓
产品大类
↓
系列 / 规格
↓
下载 / 样品
↓
询价
```

### 专业用户

```text
Google
↓
技术资料
↓
产品系统
↓
测试 / 安装 / CAD
↓
项目条件确认
```

不同页面类型不需要使用相同的行动引导。

## 18. 新站架构设计流程

推荐顺序：

```text
业务与市场
↓
竞争网站结构研究
↓
关键词主题组
↓
关键词到页面映射
↓
页面类型矩阵
↓
产品与内容层级
↓
导航
↓
URL
↓
内部链接
↓
转化路径
↓
技术验证
```

先用表格和树状结构完成，不急着进入页面视觉设计。

## 19. 旧站重构流程

旧站不能按照新站思路直接重建 URL。

先建立：

| 旧 URL | 当前职责 | 数据 / 外链 | 新职责 | 动作 |
|---|---|---|---|---|
| `/old-a/` | 产品 | 有流量 | 保留产品 | 保持 |
| `/old-b/` | 重复文章 | 很弱 | 合并到指南 | 301 |
| `/old-c/` | 已停产产品 | 有外链 | 停产说明 | 保留 / 替代 |

### 迁移前必须保护

- 已有自然流量页面。
- 已有高质量外链页面。
- 已被客户引用的技术文件。
- 已有稳定转化页面。
- 长期被搜索和内部链接使用的网址。

架构更“漂亮”不是修改稳定 URL 的充分理由。

重定向、Canonical、Sitemap 和上线验证参见 [技术 SEO](../05-optimization/technical-seo.md)。

## 22. 常见错误

### 错误 1：先画菜单，再研究搜索需求

结果往往是业务栏目和搜索页面互不衔接。

### 错误 2：一个关键词建立一个页面

容易形成大量职责相近的薄弱页面。

### 错误 3：目录越深越专业

过度嵌套增加维护成本，并不自动提升 SEO。

### 错误 4：URL 就是网站架构

Google 主要通过页面链接关系理解网站，而不是只看文件夹路径。

### 错误 5：所有内容都叫 Blog

技术资料、安装、比较、案例、工具和下载应该根据用户任务组织。

### 错误 6：重要页面只能通过搜索框找到

Googlebot 通常不会使用站内搜索框来发现所有内容。

### 错误 7：所有筛选组合都做 SEO 页面

可能制造大量重复、空页面和抓取浪费。

### 错误 8：为了新架构一次性修改所有 URL

旧站重构必须先评估历史流量、链接、转化和迁移风险。

## 23. 官方原则参考

本模块与 Google Search Central 当前公开原则保持一致，重点包括：

- 网站结构主要通过导航和页面之间的链接关系表达。
- 重要产品应能通过可抓取的 `<a href>` 链接被发现，而不是只存在于站内搜索。
- URL 应保持一致、稳定，并与内部链接、Canonical 和 Sitemap 使用同一规范版本。
- 面包屑用于表达用户能够理解的典型层级，不要求机械复制 URL 路径。
- 分页、加载更多和无限滚动必须确保后续内容仍可被爬虫通过网址和链接发现。
- 筛选导航如果不受控制，可能生成大量低价值 URL，需要在技术 SEO 阶段控制抓取和索引。

可继续参考 Google Search Central 官方资料：

- [帮助 Google 了解电子商务网站结构](https://developers.google.com/search/docs/specialty/ecommerce/help-google-understand-your-ecommerce-site-structure?hl=zh-CN)
- [电子商务网址结构最佳实践](https://developers.google.com/search/docs/specialty/ecommerce/designing-a-url-structure-for-ecommerce-sites?hl=zh-CN)
- [分页和增量加载最佳实践](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading?hl=zh-CN)
- [面包屑导航结构化数据](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb?hl=zh-CN)

## 24. 完成检查

完成网站架构前确认：

- [ ] 主要产品和业务层级已经明确。
- [ ] 每种重要页面类型都有清晰职责。
- [ ] 关键词主题已经映射到主要承接页面。
